# 1. はじめに

Rails アプリのテストでは、サーバが返した HTML を見るだけでは確認できないことがあります。

Stimulus コントローラや Turbo Frame、あるいは手書きの JavaScript が、ページの上で DOM を書き換えます。
ところが、その挙動はふだんのテストからこぼれ落ちます。

request spec も view spec も JavaScript を実行しません。そのため、スクリプトが DOM をどう変えるのかは確かめられません。
確かめようとすると、system spec、つまり Capybara で実ブラウザ(ヘッドレスブラウザ)を動かすテストに頼ることになります。
これも動作はしますが、ブラウザの起動が必要となるため、遅く、ときに flaky で、CI のセットアップも重くなります。
結果として、JavaScript の挙動はテストされないまま残りがちです。

`Dommy::Browser` は、この隙間を埋める軽量なテストブラウザです。
ページの JavaScript を、実ブラウザを起動せずに、Ruby のプロセス内で実際の DOM に対して走らせます。
レンダリング済みの HTML を渡すと、`window` と `document` を組み立て、`<script>` を実行し、`DOMContentLoaded` と `load` を発火させて、その結果の DOM を返します。
あとはその DOM を、いつもの RSpec で確かめるだけです。
ブラウザもドライバも要らず、小さなページなら一回が数ミリ秒で終わり、CI でも追加の準備なしに実行できます。

`Dommy::Browser` にできることは以下の三つです。

- DOM の組み立てと操作
- JavaScript の実行
- Capybara に似た語彙でのページ操作

フォームに値を入れ、ボタンを押し、その結果 DOM がどう変わったかを確かめる、という一連の作業をヘッドレスブラウザのプロセスなしで書けます。

一方で、軽量にするためにできないこともあります。具体的には、見た目に関わることは大幅に省略されます。
`Dommy::Browser` は CSS のカスケードと計算済みスタイルを持つので、`getComputedStyle` や `:visible` の判定は使えますが、要素を実際に配置するレイアウトエンジンは持っていません。
そのため、ピクセル単位の寸法や位置、描画の結果、ブラウザ間の差異は対象外としています。
そういった視覚的な確認は、これまでどおり system spec の領分です。

`Dommy::Browser` が受け持つのは、「この入力に対して DOM がこう変わる」というDOMレベルの挙動の層です。
system spec を置き換えるものではなく、その手前に、速くて設定のいらない層を一枚足すものです。
見た目はこれまでどおりブラウザで、挙動はここで、と分けることで、JavaScript の挙動のテストもこれまで以上に高速に行えるようにするもの、それが`Dommy::Browser` です。
